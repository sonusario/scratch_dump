# 5. The in-game computer (LanternOS)

When the character walks up to a computer and sits down, the screen zooms into a full-screen simulated desktop. The player uses it with mouse and keyboard as they would a real one. It is the game's lab, and it is how the hands-on parts of Security+ are practiced.

## Why a simulation and not real VMs

| | Simulation (chosen) | Real VMs or containers |
|---|---|---|
| Runs offline, on a phone, in a browser | Yes | No, or needs a server |
| Safe: malware, attacks and misconfigurations cannot leak | Yes | Needs careful isolation |
| Deterministic, so a task can be checked exactly | Yes | Hard |
| Story can drive it (an attacker acts at a scripted moment) | Yes | Hard |
| Fidelity of commands | Subset, chosen for teaching | Full |
| Cost to build | High once, then content-only | Hosting cost per player |

The simulation aims for **"real enough that the skill transfers"**: real command names, real flags for the common cases, real log formats (syslog, Windows event IDs, CEF), and real protocol fields in packet captures. Where it simplifies, it says so in the in-game help.

## The simulation model

Everything on every in-game computer lives in one **world network model**, so actions on one machine affect others.

```
World
├── Sites (Lantern, Harbor, Copperline, Brightwater, Paperkite, Ridgeway, Internet)
│   └── Networks (VLAN id, CIDR, zone: internal | screened | OT | guest | mgmt | cloud-vpc)
│       └── Hosts
│           ├── OS flavor: linux | windows | network-os | plc-rtos | appliance | cloud-service
│           ├── Interfaces (IP, MAC, VLAN)
│           ├── Users, groups, roles, credentials (hashed), MFA enrollments
│           ├── Filesystem (paths, owners, modes/ACLs, contents, hashes, labels)
│           ├── Processes and services (name, port, protocol, version, CVEs)
│           ├── Installed software (version, signed/unsigned, end-of-life date)
│           ├── Host firewall rules, policies (GPO / SELinux mode), baselines
│           ├── Certificates and keys (store, issuer, expiry, revoked?)
│           └── Logs (generated by the event bus)
├── Network devices (routers, switches with port security, firewalls, IDS/IPS, proxies,
│   load balancers, WAPs, VPN concentrators, jump servers, sensors, taps)
├── Cloud accounts (identities, policies, security groups, buckets, functions, containers)
├── Directory services (accounts, groups, OUs, federation trusts, SSO apps)
├── PKI (CAs, issued certificates, CRL, OCSP responder)
├── DNS zones (A, MX, TXT for SPF/DKIM/DMARC, CNAME)
└── Actors (NPC users, attackers, scheduled jobs) acting through the same API as the player
```

### Event bus

Every action, by the player, an NPC or an attacker, is an **event** (`auth.login`, `net.flow`, `file.write`, `proc.start`, `fw.drop`, `dns.query`, `cert.verify`…). Sensors and log sources subscribe to events according to where they are placed and how they are configured. That is how placement in the network diagram changes what the SIEM sees: an IDS on a tap sees flows on that segment and cannot block them; an IPS inline can block; a host with no agent sends no endpoint logs.

### Time

Simulation time runs faster than real time (default 1 real second = 1 sim minute in idle, 1:1 during active tasks), pauses in menus, and can be jumped in scripted ways ("Three hours later, the scan finishes").

### Attacker scripts

Attackers are scripts that try steps in order and check world state at each step: phishing a user, using a credential, moving laterally, escalating, exfiltrating. Each step checks the controls register (MFA required? port blocked? EDR present? segment boundary?) and either succeeds (leaving traces in logs) or fails (leaving a different trace). Scenarios read the outcome. The same scripts power Free Shift tickets.

## Shell command set

The shell is a teaching subset. Every command has `--help` and an in-game `man` page that explains what it does and why it matters for security. Unsupported commands reply with what the real one does and the nearest supported command.

### `lsh` (Linux-flavored)

| Area | Commands |
|------|----------|
| Navigation and files | `ls -la`, `cd`, `pwd`, `cat`, `less`, `head`, `tail -f`, `grep -i -r`, `find -name -perm -mtime`, `cp`, `mv`, `rm`, `file`, `strings`, `diff` |
| Permissions and users | `whoami`, `id`, `sudo`, `su`, `chmod` (octal and symbolic), `chown`, `useradd`, `usermod -L`, `userdel`, `passwd`, `chage`, `last`, `lastlog`, `getfacl`/`setfacl` |
| Processes and services | `ps aux`, `top`, `kill`, `systemctl status/stop/disable/enable`, `crontab -l`, `journalctl` |
| Network | `ip a`, `ip route`, `ss -tulpn`, `ping`, `traceroute`, `dig`, `nslookup`, `curl -I`, `nc` (connect only), `tcpdump -i -w`, `nmap` (simulated, against in-scope hosts only, with `-sS -sV -p -O`) |
| Firewall and hardening | `ufw` and a simplified `iptables`, `sestatus`/`setenforce`, `apt list --upgradable`, `apt upgrade`, `systemctl disable` |

| Logs | `/var/log/auth.log`, `/var/log/syslog`, web server logs, `grep`/`awk`-lite over them |

### Network OS (switches, routers, firewalls)

A short Cisco-like CLI for port security, ACLs, VLANs, disabling unused ports, SNMPv3 vs v2c, SSH vs Telnet, and NTP. Every concept here is also reachable from a GUI for players who prefer it.

## How computer tasks are checked

Each computer beat has a **goal predicate** over world state, not over the commands typed, so any valid way to reach the goal passes.

```yaml
goal:
  all:
    - firewall("brightwater-edge").blocks(src: "any", dst: "ot-net", port: 502, proto: tcp)
    - firewall("brightwater-edge").allows(src: "jump-01", dst: "ot-net", port: 502, proto: tcp)
    - not: firewall("brightwater-edge").has_rule_after_default_deny()
```

- **Partial credit:** the checker reports which sub-goals pass, so the player sees "2 of 3 done".
- **Side-effect check:** some goals also fail if the player broke something else (blocked the jump server, deleted the logs). The checker reports the side effect in plain words.
- **Hints:** three levels, each costing a little in-game time and noted in the shift report: (1) what to look at, (2) which app or command, (3) the exact step. Hints never cost trust.
- **Show me:** after a task, the player can watch a replay of an expert solution (Priya's), which also demonstrates other ways to do it.

## Safety rules for the simulation

- Offensive commands (`nmap`, exploit modules in the pentest range) only work against hosts marked in-scope in the current scenario's rules of engagement. Out-of-scope use is refused in character ("That's not in the SOW. Jules would get us both sued.") and teaches rules of engagement (5.3, 5.5).
- Attack content is conceptual. Payloads in the game are labelled stand-ins (for example, `' OR 1=1 --` appears as an example of SQL injection, as it does in study guides) and never working code for real targets.
- The fake internet is fully fictional. No real domains, no real brands, no outbound network access from the simulation.
