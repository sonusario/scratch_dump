# DO-178C: Software Considerations in Airborne Systems (aggregated)

**Source BoK:** RTCA DO-178C (2011) / EUROCAE ED-12C, with supplements DO-330 (tool qualification), DO-331 (model-based), DO-332 (object-oriented), DO-333 (formal methods), and DO-248C (FAQs and discussion papers).
**Why aggregated:** all RTCA documents are paid. The FAA publishes a lot of free material, but it is scattered across advisory circulars, orders, job aids, and position papers.
**Gov tie:** G1. The FAA recognizes DO-178C as an acceptable means of compliance in **AC 20-115D** for software in type-certificated aircraft (14 CFR 23/25/27/29/33/35). DoD airworthiness (MIL-HDBK-516C) also references it.

## 1. Core idea

Software assurance is scaled to the **failure condition** the software could cause or contribute to, as determined by the system safety assessment (SAE ARP4761A / ARP4754B). Higher levels → more objectives, more of them with independence.

| Level | Failure condition | Objectives (approx.) | With independence |
|---|---|---|---|
| A | Catastrophic | 71 | 30 |
| B | Hazardous / Severe-Major | 69 | 18 |
| C | Major | 62 | 5 |
| D | Minor | 26 | 2 |
| E | No safety effect | 0 | 0 |

(Counts as commonly cited for DO-178C Annex A; verify against the standard.)

## 2. Structure: the processes and their Annex A tables

| DO-178C section | Process | Annex A table | Key objectives |
|---|---|---|---|
| §4 | **Software planning** | A-1 | Plans exist and are coordinated: PSAC (Plan for Software Aspects of Certification), SDP, SVP, SCMP, SQAP; standards for requirements, design, code. |
| §5.1 | **Software requirements** | A-2 (dev), A-3 (verif.) | High-level requirements (HLR) developed from system requirements; derived requirements fed back to safety assessment; HLR accurate, consistent, verifiable, compatible with target, conform to standards, traceable. |
| §5.2 | **Software design** | A-2, A-4 | Architecture and low-level requirements (LLR) developed; LLR accurate, consistent, verifiable, traceable to HLR; architecture consistent, partitioning integrity. |
| §5.3 | **Software coding** | A-2, A-5 | Source code complies with LLR and architecture, is verifiable, conforms to standards, traceable, accurate and consistent. |
| §5.4 | **Integration** | A-2, A-5 | Executable object code produced and loaded; parameter data item files. |
| §6 | **Software verification** | A-6, A-7 | Reviews, analyses, and requirements-based testing (normal range + robustness) on target. **Structural coverage analysis**: statement (Level C), decision (Level B), **MC/DC** (Level A); data/control coupling coverage. |
| §7 | **Software configuration management** | A-8 | Configuration identification, baselines, traceability, problem reporting, change control, archive/retrieval/release, software load control, life cycle environment control. Control Categories CC1/CC2. |
| §8 | **Software quality assurance** | A-9 | Assurance that plans and standards are followed; transition criteria satisfied; software conformity review. |
| §9 | **Certification liaison** | A-10 | Communication with the certification authority; PSAC, Software Configuration Index (SCI), Software Accomplishment Summary (SAS). |
| §11 | **Life cycle data** | — | 22 data items (plans, standards, requirements data, design description, source code, executable object code, verification cases/procedures/results, SCI, SAS, problem reports, SCM and SQA records, etc.). |
| §12 | **Additional considerations** | — | Previously developed software, tool qualification (TQL-1…5 per DO-330), alternative methods, service history. |

## 3. Supplements

| Supplement | Adds |
|---|---|
| DO-330 | Tool qualification as a standalone standard; TQL levels based on criteria 1–3 and software level. |
| DO-331 | Model-based development and verification (specification vs design models, model coverage, simulation). |
| DO-332 | Object-oriented technology: inheritance (LSP), dynamic dispatch, memory management, exceptions, virtualization. |
| DO-333 | Formal methods as a replacement or complement to reviews, analysis and testing. |
